# ADR-006：per-user 身份与鉴权重构（从单共享密钥 + 匿名票到 per-user 凭证）

- **状态**：已定方向，未实施（本轮仅文档）。本 ADR 是 `docs/security-audit.md:25` G-02 残余面与 `docs/redteam-round2.md:61-70` M2-06 残余记账的**决策记录**；本轮不改 `src/`、不改 `tests/`、不新增 env。
- **背景**：
  - **现状 1 —— 凭证形态：`HERO_API_KEY` 单值，无 per-user 身份**
    - 唯一 env 网关：`src/hero_quant/config/settings.py:308` `api_key: str | None = field(default_factory=lambda: os.getenv("HERO_API_KEY"), repr=False)`——**单值**，无 user 维度、无 user↔tenant 映射表。
    - `verify_api_key`（`src/hero_quant/api/security.py:578-645`）的语义是**布尔判定**，不返回身份：缺 `expected_key` 时走 `_allow_insecure_dev`（`:618-625`），有 key 时用 `hmac.compare_digest(provided.strip(), expected_key.strip())` 做**单值**常量时间比较（`:642`），返回值只有 `True/False`。
    - `verify_hmac`（`src/hero_quant/api/security.py:443-552`）同构：secret 取 `os.environ.get("HERO_HMAC_SECRET")`（`:472`），`hmac.compare_digest`（`:529`）；对外入口 `verify_request_auth`（`:555-557`）仍只返 bool。
    - `HERO_ALLOW_INSECURE` 历史兼容开关：`src/hero_quant/api/security.py:583-604`（`=1` + `DeprecationWarning` + 非 development/非 pytest 一律阻断，`:599-604`），`HERO_ALLOW_INSECURE_DEV` 另要求 `HERO_ENV=development` + 回环 IP（`:605-617`）。
  - **现状 2 —— 签发（`POST /v1/query/ticket`）**
    - 端点：`src/hero_quant/api/server.py:1614-1615`，签名 `user: str | None = None`（查询参，**自声明**）、`scope: str | None = None`。
    - 鉴权：`_verify_key_ticket(request)` 或 `_verify_hmac_ticket(request)` 任一通过即 `_authed = True`（`:1658-1667`）——**只得到"通过/不通过"，得不到"是谁"**。
    - 身份取自自声明：`_claimed_user = _norm_uid_ticket(user)`（`:1668`），`_bound_user = _claimed_user`（`:1677`）。
    - 未鉴权分支（`:1678-1703`）：已配置 `HERO_API_KEY`/`HERO_HMAC_SECRET` 且非 `HERO_ENV=development` 且非 pytest → **401 fail-closed**（`:1691-1692`）；匿名票的自声明 `user` 被丢弃并计数告警（`:1693-1702`，G-02 发侧收敛）。
    - **已鉴权分支（`:1704-1708`）是一个 `pass`**，代码注释自认："API-Key/HMAC 现为单共享密钥，仅返回是否通过，无服务端 per-user 身份可绑定，故已鉴权签发的 `?user=` 仍为同密钥持有者互信声明……真 per-user 隔离需 per-user 密钥身份（后续专线）"。**这段注释就是本 ADR 的立项依据。**
    - 签发：`:1709-1712` `issue_ticket(ttl=SSE_TICKET_TTL_SECONDS, user_id=_bound_user, scope=_ticket_scope)`。
  - **现状 3 —— 票据载荷与消费**
    - 载荷只有两个字段：`_ticket_payload` 产出 `{"user_id": ..., "scope": ...}`（`src/hero_quant/api/security.py:83-94`）——**无签发者、无租户、无 audience、无签发时间**；匿名票 `user_id=""`（`:72-80` 归一化）。scope 白名单 `_TICKET_SCOPES = {"query","metrics","stream"}`（`:98`），归一 `_normalize_scope`（`:101-108`）。
    - 签发落 Redis：`SET key payload NX EX ttl`（`src/hero_quant/api/security.py:265-276`，键前缀 `hero:ticket:` `:35`），Redis 不可用回退进程内 `_tickets`（`:180-194`、`:280`）。
    - 消费原子且单次：`consume_ticket_with_user`（`:283-333`）走 `GETDEL` 优先（`:299`）→ Lua 原子比较删除兜底（`:312-318`）→ 未命中回查内存（`:330`、`:197-225`）；`consume_ticket`（`:336-385`）为不取身份的简化版。
    - scope 校验 `_scope_allowed`（`:139-151`）：**legacy 票（scope=None）迁移期一律放行**（`:144-145`），不匹配才 fail-closed 销毀（`:218-223`、`:301-306`）。
    - 消费端：`/v1/query`（`src/hero_quant/api/server.py:1359`，`require_scope="query"`）、`/v1/query/stream`（`:1758`，`require_scope=("query","stream")`）、`/metrics`（`:1304`，`require_scope="metrics"`，无票时回落 API-Key/HMAC `:1308-1315`）。**三处消费都只判"票是否有效 + scope 是否匹配"，不校验票背后的身份**。
    - **已解析但被丢弃**：`src/hero_quant/api/server.py:1359` 取回的 `_ticket_user_q` 在 `server.py` 内**再无引用**（全仓 grep 仅此一处）——query 面的票据身份当前完全没被使用。
  - **现状 4 —— WS 订阅侧**
    - `_consume_ticket_identity`（`src/hero_quant/api/ws.py:60-78`）消费票据并取 `user_id`；`_resolve_identity_channel`（`:81-106`）：`ticket_user` 非空 → 派生 `ws:channel:{user}`（`:102`，前缀 `ws:channel:` `:114`），`claimed` 与 `ticket_user` 不一致 → 返回 `(None, reason)` 视为冒充（`:100-101`）；匿名票（`""`）**忽略 `?user=`**、一律 per-connection 频道（`:103-106`）。
    - 端点两处：`/ws/trace`（`src/hero_quant/api/ws.py:396-428`，消费 `:412`、派生 `:419`、mismatch → **4001 关闭** `:420-424`）、`/ws/query`（`:469-492`，消费 `:476`、派生 `:483`、mismatch → 4001 `:484-488`）。
    - 频道解析 `resolve_user_channel`（`:130-144`）：超长 user 降级为 per-connection 防串扰（`:137-139`）。
  - **现状 5 —— 共享密钥互信的爆炸半径**
    - 签发限流按 **IP** 而非身份：`src/hero_quant/api/server.py:1640` `limiter.try_acquire_sync(f"ticket:{client_ip}", 10, 60)`（键经 `src/hero_quant/infra/redis.py:53` 自动加 `hero:ratelimit:` 前缀）。
    - 通用限流的租户维度依赖 `request.state.current_tenant` / `current_user`（`src/hero_quant/api/rate_limiter.py:34-52`、`:55-63`），而**本仓无任何代码写入 `request.state.current_tenant` / `current_user`**（`server.py` 内 `request.state` 仅 `:521` 一处读取，无写入点）→ 该租户维度当前恒为 `None`，限流键恒为 `user:`/`ip:` 旧形态。
    - 结论：**任一持有 `HERO_API_KEY`（或 `HERO_HMAC_SECRET`）者，可签发任意 `user` 的绑定票**（`src/hero_quant/api/server.py:1668`+`:1677`+`:1710`），并经 `ws:channel:{user}`（`src/hero_quant/api/ws.py:102`）订阅该用户的 trace/query 进度流；`docs/security-audit.md:31` 的定级"任一持 key 调用方可订阅任意用户频道"在**已鉴权**路径上仍然成立（匿名路径已由 G-02 双侧闭合）。这就是 `docs/redteam-round2.md:68-70` 记的残余中危（"记账 → D/鉴权重构专线"）。
  - **目标模型（建议 / 待定，非现状）**
    - **建议**引入 per-user 凭证：形如 `user_id + secret` 的 user-scoped credential，服务端可查到 `user_id → tenant` 绑定。**凭证的存储介质（PG 表 / Redis 哈希 / 外部 IdP）待定**。
    - **建议**签发/轮换/吊销三件套：签发返回明文一次（仅此一次可见）、轮换走双凭证重叠窗口、吊销即刻生效（吊销清单需在票据消费侧被校验，否则旧票在 TTL 内仍可用）。**轮换重叠窗口长度、吊销生效时点待定**。
    - **建议**`user ↔ tenant` 绑定为多对多或一对多（一个 user 可属多个 tenant、一个 tenant 可有多个 user）——**具体基数待定**；但必须**与 billing 账本的 tenant 词表一致**（`src/hero_quant/billing/service.py:86`、`:96-97`；`migrations/002_billing_rls.sql:15`、`:23-24`），否则 tenant 维度在两个存储间对不齐。
    - **建议**票据载荷扩展为 `{"user_id", "tenant", "scope", "audience", "iat", "jti"}`，其中 `jti` 供吊销清单比对、`audience` 绑定端点集合。**字段集与编码格式待定**（须与既有 `_ticket_payload` 载荷保持向后兼容解析）。
    - **建议**鉴权通道：HTTP 面用 per-user API key 换一次性 user 票据（票据承载身份），WS 订阅用票据 + 身份一致性校验（沿用既有 `src/hero_quant/api/ws.py:81-106` 的 mismatch → 4001 语义，扩展为"票身份 vs 声明身份 vs 凭证身份"三方一致）。
    - **建议**把 `user → tenant` 注入 `request.state.current_tenant` / `current_user`，让既有租户感知限流（`src/hero_quant/api/rate_limiter.py:34-63`）与回测缓存键（`src/hero_quant/api/server.py:2100-2112`）真正拿到租户维度。**注入点建议在签发/消费票据之后、端点业务逻辑之前。**
- **决策**：
  - **分步迁移路径**（每步标出兼容性、回退开关、对现网调用方的影响面）：

    | 步 | 内容 | 兼容性 | 回退开关 | 对现网调用方的影响面 |
    |---|---|---|---|---|
    | 0 | 引入 per-user 身份解析层（`resolve_principal` 之类），**旁挂**、不改现有签发/消费路径；同时补 `request.state.current_tenant` / `current_user` 写入点 | 完全向后兼容（新层不参与鉴权判定） | 无需开关（新层无行为） | 无 |
    | 1 | 凭证层支持 per-user：新增 user-scoped 凭证的签发/轮换/吊销 API 与存储；`verify_api_key` 扩展为"返回 principal 或 None"，**保留原 bool 入口** | 向后兼容（旧 bool 入口保留） | `HERO_AUTH_MODE=shared`（默认）关闭 per-user 解析 | 仅管理面调用方（新增接口） |
    | 2 | 签发侧绑定服务端身份：`_bound_user` 改由**服务端 principal 派生**，`?user=` 自声明一律丢弃（G-02 发侧语义从"匿名丢弃"扩展到"已鉴权也丢弃"） | **破坏性**：已鉴权调用方若依赖 `?user=` 签特定 user 的票，将改为签到自己的票 | `HERO_AUTH_MODE=shared` 恢复旧行为 | 已鉴权调用方（`?user=` 变为无效参数） |
    | 3 | 票据载荷扩展（`tenant` / `audience` / `iat` / `jti`）+ 消费端校验；**legacy 票（无新字段）在迁移期放行** | 向后兼容（解析层双格式） | 载荷扩展由 flag 控制；legacy 放行窗口设**明确截止期** | 无（消费格式兼容） |
    | 4 | WS 订阅鉴权收紧：三方身份一致（票身份 / `?user=` 声明 / 凭证身份）；per-user 模式下 `?user=` 与票不一致即 4001 | 破坏性（`shared` 模式下不变） | `HERO_AUTH_MODE=shared` | WS 调用方（`?user=` 需与票一致） |
    | 5 | 关闭 `shared` 模式：单一 `HERO_API_KEY` 退役或降级为管理面专用；`?user=` 参数从 API 表面移除 | 破坏性 | 需保留一个版本的降级窗口后再删 | 全部调用方（须先迁到 per-user 凭证） |

  - **回退开关的历史经验（`HERO_ALLOW_INSECURE`）**：`src/hero_quant/api/security.py:583-604` 给出可复用的范式——(a) 兼容开关**默认关闭**（生产 fail-closed，`src/hero_quant/api/security.py:599-602`）；(b) 命中即 `DeprecationWarning` + 结构化 warning 可观测（`:591-596`、`:603`）；(c) 开关**不改变**既有 fail-closed 语义，只收口可观测性。**建议**本 ADR 的 `HERO_AUTH_MODE` 沿用同一范式：默认 `shared`（当前行为）、per-user 为 opt-in、命中旧模式记 warning、删除待后续版本（与 G-11 的"删除该分支待后续版本由 D 线评估单测影响"口径一致，`docs/security-audit.md:108`）。
  - **与 G-02 / G-06 / G-11 已落地项的衔接**（**在已落地语义之上继续演进，不得推翻**）：
    - **G-02**（`docs/security-audit.md:25-34`）：发侧已收敛为"匿名票丢弃自声明 `?user=`"（`src/hero_quant/api/server.py:1693-1702`），订阅侧已收敛为"匿名票一律 per-connection + 票/声明不一致 4001"（`src/hero_quant/api/ws.py:100-106`、`:420-424`、`:484-488`）；K 线 G-08 在其上**叠加** scope 分域，未改其语义（`docs/security-audit.md:147`）。**本 ADR 承接而非替换**：步骤 2 只是把"发侧丢弃自声明"从**匿名条件**扩展到**全部条件**（因为已鉴权时服务端有 principal 可用），订阅侧的三方一致校验是既有 mismatch → 4001 语义的加严，**方向一致、覆盖面扩大，不改判据**。
    - **G-06**（`docs/security-audit.md:67-73`）：票据签发限流已修为 **fail-closed**（`src/hero_quant/api/server.py:1631-1651`：Redis 异常 → `_inc_api_error("ticket","ratelimit_unavailable")` + warning `ticket.ratelimit_failed_503` + **503**）。**本 ADR 不得放宽该语义**；步骤 1 之后建议把限流键从 IP（`src/hero_quant/api/server.py:1640`）升级为"IP + principal"（这属于 G-07 已落地的租户混键思路在签发面的延伸，`docs/security-audit.md:75-80`），**须另立 ticket**。
    - **G-11**（`docs/security-audit.md:104-108`）：`HERO_ALLOW_INSECURE` 已加固但**保留待后续版本删除**。**本 ADR 不删除该开关**，仅在 `HERO_AUTH_MODE` 迁移说明中标注二者关系（`HERO_ALLOW_INSECURE` 属"无凭据"降级、`HERO_AUTH_MODE` 属"多用户"降级），并把"两开关同时退役"列为**待用户决策项**。
    - **G-08**（`docs/security-audit.md:82-86`）：scope 分域（`src/hero_quant/api/security.py:98`、`:139-151`）**保持不变**；步骤 3 的 `audience` 是 scope 的**正交扩展**（scope 判"端点类"，audience 判"实例/受众"），二者**并存**而非互相替代，legacy 票放行窗口（`src/hero_quant/api/security.py:144-145`）沿用同一截止期口径。
  - **风险**
    - **冒充面残留**：在步骤 2 落地前，任一持共享密钥者仍可签任意 user 的绑定票并订阅其频道（`src/hero_quant/api/server.py:1668`+`:1677`+`:1710` → `src/hero_quant/api/ws.py:102`）。**这是当前已存在的敞口，本 ADR 不解决存量，只收敛路径**——残留期长度由步骤 2 的落地时间决定，属**待用户决策**项。
    - **共享密钥泄露半径**：单一 `HERO_API_KEY`（`src/hero_quant/config/settings.py:308`）一旦泄露，攻击面 = 全部用户 + 全部 tenant（因为密钥本身不携带租户维度）；per-user 化后泄露半径收敛为单 user，但**签发接口本身**（步骤 1 新增）会成为新的高价值目标，需与签发限流（`src/hero_quant/api/server.py:1640`，IP 维度）协同。
    - **迁移期双轨鉴权的歧义**：`shared` 与 `per_user` 并存时，同一请求可能命中两条路径（票据里带 user，凭证也带 user，二者不一致时**谁优先**必须写死在实现里）。**建议**：`per_user` 模式下以**凭证 principal 为准**，票据中的 `user_id` 与之不一致即 fail-closed 销毀（不做"取其一"的静默降级）——**该优先级规则待确认**。
    - **审计与追责缺口**：现状下服务端**不持有"谁用了这张票"的可信记录**——票据载荷无签发者（`src/hero_quant/api/security.py:83-94`），`/v1/query` 解析出的身份被丢弃（`src/hero_quant/api/server.py:1359`），`request.state` 无身份写入点（`src/hero_quant/api/server.py:521` 只读）。因此"某次订阅/查询是谁做的"当前**无法事后追溯**。per-user 化后可追责，但需要**审计留存面**（保留期、字段、脱敏口径）——**待定**。
    - **兼容窗口失控**：G-08 的 legacy 票放行（`src/hero_quant/api/security.py:144-145`）已示范——无明确截止期的"迁移期放行"会让分域**永久停在纸面**（`docs/redteam-round2.md:76-77` 已就此提醒）。本 ADR 的每一步放行窗口都必须带**明确截止日**。
- **后果**（正面）：把"鉴权通过"升级为"**鉴权到人**"——服务端第一次同时持有 `user_id` 与 `tenant`，从而使 billing 账本的 tenant 维度（`src/hero_quant/billing/service.py:86`、`:96-97`）、checkpoint 的 tenant 维度（`src/hero_quant/checkpoint/postgres.py:77`）与限流/缓存的租户维度（`src/hero_quant/api/rate_limiter.py:34-63`）有了**共同的绑定源**；WS 的 `ws:channel:{user}` 隔离从"同密钥持有者互信"变成"仅本人可入"；`/v1/query` 丢弃的票据身份（`src/hero_quant/api/server.py:1359`）得以真正使用，审计与追责从"不可能"变为"可设计"；G-02 遗留的"后续专线"（`src/hero_quant/api/server.py:1705-1707` 注释、`docs/redteam-round2.md:70`）有了明确落点；凭据可轮换/可吊销，密钥泄露的爆炸半径从"全体用户"收敛为"单个 user"。
- **后果**（代价/约束）：本轮**零代码落地**，全部结论为方向性；步骤 2、4、5 是**破坏性变更**，现网调用方必须先迁到 per-user 凭证，且迁移窗口内**双轨并存**会带来判读成本与优先级歧义（需写死并单测锁定）；引入 per-user 凭证 = 引入**凭证生命周期管理**（签发/轮换/吊销/审计留存），这是长期运维负担，不是"改一行就能完成"的事；凭证存储、吊销清单、审计留存的**具体方案均待定**，本 ADR 不预设；步骤 3 的票据载荷扩展会触及票据解析的向后兼容（`src/hero_quant/api/security.py:83-94`、`:154-177`）与 legacy 放行窗口（`:144-145`），需与 G-08 的窗口**统一截止期**，否则出现两套窗口；`HERO_ALLOW_INSECURE`（`src/hero_quant/api/security.py:583-604`）与 `HERO_AUTH_MODE` 两个降级开关并存会放大配置歧义，是否合并/同期退役**待用户决策**；本 ADR 不触碰 `migrations/`、不新增 env 落盘，实施时须走 `settings.py` env 网关（AGENTS §2 三处联动：`.env.example` + `settings.py` + README env 表）。
