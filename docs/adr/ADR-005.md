# ADR-005：billing tenant 归属（`purchases.tenant` 卖家列与账本归因）

- **状态**：已定方向，未实施（本轮仅文档）。本 ADR 是 `docs/security-audit.md:36` G-03 的**决策记录**；本轮不改 `src/`、不改 `migrations/`（冻结区，AGENTS §1）。
- **背景**：
  - **现状 A —— billing 账本的 tenant 键：谁写、写到哪一列**
    - 写者：`BillingService.publish_factor`（`src/hero_quant/billing/service.py:327-337`）的 `tenant` 是**调用方显式入参**（默认 `"default"`，`:332`），非空校验在 `:342-343`；落库前组装 factor dict（`:367-373`），`tenant` 原样进 `factors.tenant`（DDL `:86`，复合唯一 `UNIQUE (factor_id, tenant)` `:88`）。
    - 买侧：`BillingService.purchase`（`src/hero_quant/billing/service.py:748-755`）的 `buyer_tenant` 同样是**调用方显式入参**（`:764-765` 校验）；因子查找先按买方域查（`:768`），miss 后允许跨租户全局命中（`:770-771`，marketplace 语义）。
    - 收据构造（真 PG 分支）`src/hero_quant/billing/service.py:865-873`：`"buyer_tenant": buyer_tenant`（`:867`）、**`"tenant": buyer_tenant`（`:868`）**；emulated/内存分支同形（`:947-955`，`:950`）。按 `_PURCHASE_INSERT_SQL` 的列序 `factor_id, buyer_tenant, tenant, price, idempotency_key`（`src/hero_quant/billing/service.py:143-147`），第 3 列就是"卖家列" `purchases.tenant`。
    - 落库时该列被**再写一次 buyer**：`_pg_insert_purchase_sync` 取 `_tenant = str(receipt.get("buyer_tenant") or receipt.get("tenant") or "default")`（`src/hero_quant/billing/service.py:1011`），`_params` 第 2、3 位同为 `_tenant`（`:1016-1022`），`SET LOCAL app.tenant` / `app.current_tenant` 也是这个 buyer（`:1028`、`:1036`）。
    - 账本（ledger）同样只记买方：`ledger.append(..., tenant=buyer_tenant)`（真 PG 分支 `src/hero_quant/billing/service.py:911`、emulated 分支 `:972`）；发布侧则是 `tenant=tenant`（`:402`、`:423`、`:453`、`:490`）。
    - RLS 按列分家：买家看 `buyer_tenant`（`src/hero_quant/billing/service.py:124` / `migrations/002_billing_rls.sql:53-54`），卖家看 `tenant`（`src/hero_quant/billing/service.py:126` / `migrations/002_billing_rls.sql:56-57`），插入只校验 `buyer_tenant = current_tenant()`（`src/hero_quant/billing/service.py:128` / `migrations/002_billing_rls.sql:58-60`），更新/删除只对卖家开放（`src/hero_quant/billing/service.py:130`、`:132` / `migrations/002_billing_rls.sql:62-66`）。
    - **现状结论**：`purchases.tenant` 这一列在应用侧**恒等于 buyer**，卖家维度在"收据 → 账本 → 落库"三处全部丢失；而 RLS 的卖家可见性 policy 正是按这一列判（`migrations/002_billing_rls.sql:56-57`），因此卖家经 `purchases_seller_select` 永远看不到自己售出的单。
  - **现状 B —— checkpoint PG 的租户键推导**
    - `thread_id` 是三段式 `workflow:run:tenant`，校验在 `src/hero_quant/checkpoint/postgres.py:310-319`；`_thread_to_keys` 拆成 `(tenant, thread, seq)` 并做 seq 分配与线性探测（`:322-371`，映射键含 DSN 前缀做跨库隔离 `:331-337`、`:344`）。
    - 存储键：`_pg_store_key(dsn, thread_id) = sha256(dsn)[:12] + "::" + thread_id`（`:178-184`）——**tenant 只作为 `thread_id` 的一段隐式参与**，不单独成键。
    - 锁键：`_pg_lock_key(tenant, thread, seq) = sha256(f"{tenant}::{thread}::{seq}")` 取模 `2**63-1`（`:223-229`），用于 `pg_advisory_xact_lock`（`:850`）。
    - 落库：`checkpoints` 主键 `(tenant, thread, seq)`、`tenant text NOT NULL CHECK (tenant <> '')`（`:77`、`:83`）；UPSERT `ON CONFLICT (tenant, thread, seq) ... WHERE checkpoints.version <= EXCLUDED.version`（`:775-778`）。
    - 读序 SQL 以 `tenant=%s AND thread=%s AND seq=%s` 为准（`:233`）；legacy 表 `checkpoints_legacy` 无 tenant 维度（`:234`、`:93-97`）。
    - fail-closed：run 映射缺失抛 `MissingRunMapping`（`:256-259`、`:401-406`），禁止用 seq 冒充 run 覆盖他人 checkpoint。
  - **现状 C —— `_Saver` 双写：checkpoint 与 billing 各自落库**
    - server 侧 checkpoint 落库由 `_Saver`（`AsyncPostgresSaver`）承接：`src/hero_quant/api/server.py:355`/`:357`（emulated 分支）、`:382`/`:384`（PG 不可达分支）、`:402-405`（正常分支），并在请求链上以 `checkpoint`/`checkpointer` 注入 AgentLoop（`:1520`、`:1540-1543`、`:1775`、`:1912`）。
    - billing 侧在 server 内**只出现一次**：`BillingService(dsn=dsn)`，且仅用于 `/ready` 探针（`src/hero_quant/api/server.py:1097`，探针 `_check_billing_pg` `:1085-1094`）。
    - 两库 tenant 词表**无绑定**：checkpoint 的 tenant 取自 `thread_id` 第三段（调用方拼串），billing 的 tenant 取自函数显式入参；`server.py` 内没有把鉴权身份写入任一 tenant 的代码路径（限流键的 tenant 来自 `request.state`，见 `src/hero_quant/api/server.py:516-527` 与 `src/hero_quant/api/rate_limiter.py:34-52`，而 `request.state.current_tenant` / `current_user` 在本仓**无写入点**）。
    - **事实（关键）**：`src/` 下**无** `publish_factor` / `purchase()` 的生产调用方。`server.py` 路由表只有 `/live`（`:874`）、`/ready`（`:1212`）、`/metrics`（`:1296`）、`/v1/query`（`:1340`）、`/v1/query/ticket`（`:1614`）、`/v1/query/stream`（`:1715`）、`/v1/backtest/metrics.json`（`:2276`）、`/v1/backtest/positions.csv`（`:2292`）、`/v1/backtest/tearsheet.html`（`:2309`）、`/v1/backtest/drawdowns.json`（`:2412`）、`/v1/trace/events`（`:2435`）——**无计费售卖端点**（`docs/arch/billing.md:34` 记的上游"`/v1/*` 售卖路径"是 2026-10-19 旧快照，与当前路由表不符）。故 G-03 的触发路径当前是**潜伏态**（代码存在、无调用方），一旦补上售卖端点即立刻变为可达。
  - **影响面**
    - 触发路径（真 PG、buyer≠seller）：`purchase` → `_pg_insert_purchase_sync`（`src/hero_quant/billing/service.py:1002`）→ INSERT（`:1043-1054`）时 `purchases.tenant` 与 `factors.tenant` 不一致 → 复合 FK `(factor_id, tenant) REFERENCES factors(factor_id, tenant) ON DELETE RESTRICT`（`migrations/002_billing_rls.sql:27-28`）违例 → 异常上抛 `src/hero_quant/billing/service.py:876-878` → **买单不可用（可用性断点）**。
    - 触发路径（emulated/内存）：`src/hero_quant/billing/service.py:947-955` 静默落 buyer 归属行、`:968-974` 账本只记 buyer → **无异常、无对账信号**，卖家维度永久丢失（**财务归因断点**；`docs/redteam-round2.md:44-50` M2-04 已独立记账，定级"中"）。
    - 账本与收据两侧都缺卖家维度（`src/hero_quant/billing/service.py:868`、`:911`、`:972`），`attribution()`（`:1150-1180`）只能按 `factor_id` 聚合，`list_purchases(tenant)`（`:1182-1191`）只按 `buyer_tenant` 过滤 → 卖家收入无法从任一存储侧归集。
    - 受影响表与约束（引用 `migrations/002_billing_rls.sql`，**本轮不改**）：`factors`（`:10-19`，复合唯一 `:17-18`）、`purchases`（`:20-29`）、复合 FK（`:27-28`）、`ENABLE + FORCE ROW LEVEL SECURITY`（`:36-40`）、6 条 policy（`:42-46`、`:53-66`）、`current_tenant()`（`:3-8`）、存量回填说明（`:69-72`）、管理角色 BYPASSRLS 口径（`:73-75`）。
    - `/ready` 与降级语义**不得被本 ADR 弱化**：`HERO_BILLING_DSN` 缺配即 fail-closed（`src/hero_quant/config/settings.py:203-214`，共享库须 `HERO_BILLING_ALLOW_SHARED_DB` 显式 opt-in `:216-218`、`:219-230`），`/ready` 以 `billing` 模式 + reason 显式暴露（`src/hero_quant/api/server.py:1230`、`:1241`、`:1250-1252`、`:1258-1259`、`:1283`）——这是 ADR-002 的既定语义。
- **决策**：
  - **分步迁移路径**（4 步实施 + 1 步退役；每步给出观测点与回滚方式）：

    | 步 | 内容 | 需 DDL？ | 可验证观测点 | 回滚方式 |
    |---|---|---|---|---|
    | 0 | 只读诊断：统计 `buyer≠seller` 的购买占比与 FK 违例计数（结构化日志 + `/ready` reasons），不改任何写入语义 | 否 | 日志出现 `billing.tenant_mismatch` 计数；`/ready` `reasons["billing"]` 可见 | 纯只读，回滚 = 撤诊断代码 |
    | 1 | 应用侧写对卖家列：`purchase` 解析 factor 的 seller tenant 写入 `purchases.tenant`；`SET LOCAL` 仍用 buyer 以满足 `purchases_insert`（`src/hero_quant/billing/service.py:128`） | 否 | FK 违例计数归零；卖家经 `purchases_seller_select`（`migrations/002_billing_rls.sql:56-57`）可见自己售出的单 | env 开关 `HERO_BILLING_SELLER_TENANT=0` 关闭新列语义，回落现状 |
    | 2 | 账本/归因口径拆分：`ledger.append` 同时携带 buyer 与 seller 维度；`attribution()`（`src/hero_quant/billing/service.py:1150-1180`）按 seller 维度出账 | 否 | `attribution()` 返回值新增 seller 口径且与 purchases 侧对账一致 | env 开关回退到旧口径（保留双写期字段） |
    | 3 | 存量回填 + 约束收紧：把历史 `purchases.tenant = buyer_tenant` 的行按 `factors` 反查回填为卖家 tenant，并对存量补建复合 FK 校验 | **是 —— `migrations/` 冻结区，须另立专线并由用户批准**（AGENTS §1） | 回填后存量行 seller 维度非空比例 = 100%；复合 FK 校验全绿 | 回填脚本反向 UPDATE 还原；DDL 回滚走专线 |
    | 4 | 退役旧语义：emulated/内存分支（`src/hero_quant/billing/service.py:947-955`）与收据 `tenant` 字段的旧含义一并收敛；旧收据字段标 deprecated | 否 | 全仓 `grep` 旧字段消费点为 0；单测锁定新语义 | 保留 deprecated 字段一个版本周期，可回退读路径 |

  - **每步的兼容性窗口**：步骤 1、2 为"**双写/双读**"期（新列写新值，旧读路径同时兼容两种取值），窗口内新旧读路径必须都能解析 `tenant`；步骤 3 起进入"**只读新值**"期；步骤 4 才是"**只写新值**"期。步骤 3 之前不得移除任何旧字段。
  - **风险与回滚**：
    - 步骤 0 风险：无写入风险；爆炸半径=日志量。回滚判据：日志噪声影响 `/ready` 响应体时立即撤。
    - 步骤 1 风险：卖家列写对后，`purchases_seller_update/delete`（`src/hero_quant/billing/service.py:130`、`:132` / `migrations/002_billing_rls.sql:62-66`）的可见域随之扩大——原先看不见自己单据的卖家开始获得更新/删除权限，**这是权限面扩大而非纯粹修正**，需在同一步内确认这两条 policy 的期望。爆炸半径：跨租户购买单据的 seller 可见性 + 归因账目。回滚判据：`HERO_BILLING_SELLER_TENANT=0` 关闭后 FK 违例计数回升、卖家可见性退化为零。
    - 步骤 2 风险：账本双写期两侧口径不一致（收据带 seller、账本只有 buyer），对账脚本可能误判。爆炸半径：仅账本/归因读侧。回滚判据：对账差异率超过迁移前基线即回退。
    - 步骤 3 风险：**唯一涉及 DDL 的一步**，回填写错将污染资金数据；`FORCE RLS` 下回填需在同一事务内 `SET LOCAL`（`migrations/002_billing_rls.sql:69-72` 已给出回填口径），否则 `current_tenant()` 为 NULL 会导致零行匹配（与 G-04 同型风险）。爆炸半径：全量 `purchases` 历史行。回滚判据：回填后行数/金额汇总与迁移前快照不一致即回滚（必须先做迁移前快照）。
    - 步骤 4 风险：老收据（无 seller 字段）失去解释。爆炸半径：历史收据的展示与导出。回滚判据：deprecated 字段保留期内可回退。
    - **全流程回滚判据**：`/ready` 的 `billing` 维度由 `pg` 退化、FK 违例计数非零、或对账差异率超基线，三者任一即整体回滚到步骤 0 状态。
  - **与 G-03 的关系**：本 ADR 是 G-03 的**决策记录**（G-03 原文 `docs/security-audit.md:36`）。其证据位点按 2026-10-19 审计快照写作 `billing/service.py:978,835` + `migrations/002_billing_rls.sql:28,58`——**前者的行号在当前树已漂移**：现树等价位点为收据 `tenant` 恒为 buyer（`src/hero_quant/billing/service.py:868`、`:950`）与落库第 3 列恒为 buyer（`:1011`、`:1016-1022`）；后者 `migrations/002_billing_rls.sql:28`（复合 FK）、`:58`（"seller tenant 由应用显式提供"注释）至今未变。**本轮不实施**。`docs/security-audit.md:146` 与 `:158` 记的"K 线红线不动 G-03，待 billing 架构专线"**理由仍然成立**，具体为：(a) 修复不是单点热修——同一条写入要同步改收据语义（`src/hero_quant/billing/service.py:868`）、INSERT 列序（`:143-147`、`:1011-1022`）、账本归因（`:911`、`:972`）、存量数据四处；(b) 收据 `tenant` 字段被 `attribution()` 的去重键依赖（`src/hero_quant/billing/service.py:1168` 的复合键含 `tenant`），改语义会牵动历史去重口径；(c) 跨租户购买的可用性断点要求"先可观测（步 0）→ 再改写（步 1-2）→ 后收紧（步 3）"三段窗口，而 `migrations/` 是冻结区（AGENTS §1），存量回填必须另立专线并由用户批准。
- **后果**（正面）：把"卖家归属"从隐式约定变成显式列语义 + 显式账本字段，财务归因闭环（`purchases` / ledger / `attribution()`）三侧口径可对齐；真 PG 跨租户购买从"必然 FK 违例"变为可成功，市集可用性恢复；RLS 的买家/卖家双可见性 policy（`migrations/002_billing_rls.sql:53-57`）第一次真正有意义——当前 `purchases_seller_select` 恒空转；本 ADR 把 G-03 从"安全审计里的一条记账"升级为有步骤、有观测点、有回滚判据的架构决策，K 线红线的"待专线"因此有了可执行的落点。
- **后果**（代价/约束）：迁移期必须维持"双写/双读"兼容窗口，读路径复杂度上升（同一字段两种含义），期间任何绕过新语义的直写都可能污染归因；步骤 1 会扩大卖家的更新/删除可见域（权限面扩大需显式确认）；步骤 3 触及 `migrations/` 冻结区，**必须另立专线 + 用户批准**，本 ADR 不构成实施授权；步骤 3 的存量回填在 `FORCE RLS` 下有与 G-04 同型的"静默零行匹配"风险（`migrations/002_billing_rls.sql:69-72`），必须先做迁移前快照与回填后汇总比对；billing 与 checkpoint 的 tenant 词表在本 ADR 中**不统一**——checkpoint 侧 tenant 来自 `thread_id` 第三段（`src/hero_quant/checkpoint/postgres.py:310-319`），两侧绑定问题由鉴权重构方向另行处理（见 ADR-006）；本轮零代码改动，实施责任落在后续 billing 专线。
