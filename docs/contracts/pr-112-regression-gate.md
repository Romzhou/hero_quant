# PR-112 回归门口径（2026-11-01 定稿，批次16）

> 状态：**已定，不再讨论**。本文件只定义口径，评测脚本另立 PR；本批不实现。
> 背景：真实评测当前 36/50 = 0.72，网关不回 usage、成分为 estimated；p95 延迟约 66s。

## 1. 四条口径

| 维度 | 口径 | 初值 / 现状 |
|---|---|---|
| **成本** | 不设金额上限，设**调用次数上限** | 500 次/天（跑一轮后按实测调） |
| **延迟** | **只记录，不判定** | p95 ≈ 66s 是模型速度，不是代码质量；仅写入报告 |
| **质量** | 回归门只看质量分 | 底线 **0.70**（当前 0.72，余量 0.02） |
| **跑法** | 发版前**手动跑一次**，不进 CI | 50 条 × 66s ≈ 55 分钟，不适合每次 push |

## 2. 为什么成本按次数而不是金额

当前 LLM 源是免费/无 usage 回传：没有可信的 token 计量，按金额判定等于用估算值当门禁。
次数是可精确观测的事实（每次调用 +1），不会因为网关改口径而漂移。

定价层（`4ec3637` + 批次15 的 `HERO_PRICING_BACKEND`）已经就绪：将来接入付费源、
后端回传真实 usage 后，**只需把「次数上限」换成「金额上限」**，业务代码不动 —— 定价 provider
换 `catalog`→付费价目即可。

## 3. 为什么延迟不设门

- p95 66s 主要来自模型推理与排队，不是本仓库代码路径；
- 用延迟做门会把「上游变慢」判成「代码回归」，长期必然被绕过（改成 skip 或调阈值）；
- 但延迟必须**记录并随报告输出**：出现数量级变化（如 66s → 600s）时人工介入。

## 4. 质量门 0.70 的由来

- 当前实测 36/50 = 0.72（批次 8 二段式总结后从 0.36 提升）；
- 底线取 0.70，留 0.02 余量吸收评测抖动；
- 低于 0.70 视为回归，先看失败样本分类（工具调用、总结、引用），再决定回滚还是修。

## 5. 执行清单（发版前）

1. 起本机 LLM 网关（凭据只在 `/tmp/hero-llm.env`，绝不入库）；
2. `python scripts/eval_real.py`（或在 `scripts/eval_agent.py` 里跑 50 条）；
3. 记录并归档：质量分、失败样本、调用次数、p50/p95 延迟、usage_source 分布；
4. 质量分 ≥ 0.70 才发版；延迟与成本只写进报告，不阻断。
