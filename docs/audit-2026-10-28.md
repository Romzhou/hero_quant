## 2. 五类问题分型（统一词表）

审查中最大的误解来源是"没实现"和"实现了但不生效"被混为一谈。按下面五类归档：

| 类型 | 定义 | 实例 |
|---|---|---|
| **real** | 代码正确 + 生产可达 + 实测生效 | 回测引擎、pandas 指标、hash 账本、腾讯日线 |
| **有实现无路径** | 代码正确、单测覆盖，但生产触发条件永不满足 | 1% 跨源比对、`MemoryStore`、`checkpoint`、`GroundingLedger` |
| **有实现未接线** | 组件建好、甚至 `/ready` 探活，主链路不调用 | `app.state.memory_store`、`get_saver` |
| **stub** | 返回常量/合成数据，且**没有**正确的降级标记 | `_FakeLLM`、`graph.py` 节点、`get_ticker_info` |
| **broken** | 依赖缺失/配置矛盾，直接跑不通 | 镜像缺 4 包、`/ready` 恒 503、`run_backtest` PIT |

**判据（可直接复用）**
- 找死代码：`grep` 主函数调用点，0 调用点 = 无路径。
- 找假门：有调用点就查门控形参在调用方是否被赋值，恒 `None/False` = 门永不打开（`run_backtest`、`loop.checkpoint`、`loop.memory_store`）。
- 找假成功：见 §4 的三层检验。

## 3. 阻断级：容器 + 数据库的五层断点

用户直觉"容器/数据库跑不起来"是准确的，拆开是 5 个独立断点，**任一层单独成立就足以起不来**：

| # | 断点 | 位置 | 实测 | 归属 |
|---|---|---|---|---|
| 1 | compose 缺 `.env` 直接拒绝解析 | `docker-compose.yml:81-82` | `docker compose config` exit 1：`env file .env not found` | 部署 |
| 2 | 镜像缺运行时依赖 | `requirements-lock.txt`（无 redis/psycopg/psycopg_pool/slowapi）+ `Dockerfile:40 --no-deps` | 镜像内 4 个包 `import` 全 False | 部署 |
| 3 | 无 Redis → 限流 fail-closed 成 429 | `infra/redis.py:309` | 容器内 `GET /v1/query` → 429；`POST /v1/query/ticket` → 429 | D |
| 4 | `/ready` 永不绿 | `server.py:1248`（缺 `COHERE_API_KEY` 即 degraded） | 冷启动 32.1s 才 503；compose 与 `.env.example` 都没给这个 key | D |
| 5 | 健康检查只探 `/live` | `Dockerfile:100-101` | 上面全挂，容器仍显示 healthy | 部署 |

**第 4 层的连带伤害**：`_ready_run_with_timeout`（`server.py:933`）本来是为防 30s 卡死写的，但**从未被调用**（死代码）；`/ready` 直接走 `pool.connection()` 默认 30s 超时。

- `server.py:323` 默认 `dsn="memory://default"`；`:352-367` 非 `HERO_CHECKPOINT_TRY_PG=1` 一律返回 emulated 内存桩；compose 没设这个变量。
